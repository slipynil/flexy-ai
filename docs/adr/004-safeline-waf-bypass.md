# ADR-004: Обход SafeLine WAF на flexy-ai.com

- **Статус:** Принято
- **Дата:** 2026-11-07

## Контекст и проблема

7.11.2026 flexy-ai.com закрыл весь сайт (включая `wp-admin/admin-ajax.php`) WAF'ом
SafeLine (Chaitin 雷池, `server: Tengine`). Любой клиент без браузера (python-requests,
curl — проверено) получает нестандартный **HTTP 468** и HTML-страницу JS-челленджа
вместо контента. Челлендж:

- требует подтверждения «Confirm You Are Human» (клик) и клиентской верификации;
- детектит автоматизацию через библиотеку devtools-detector — чекеры
  `regToStringChecker` / `functionToStringChecker` / `dateToStringChecker` /
  `devtoolsFormatterChecker` / `performanceChecker` кладут в `console.log` объект
  с getter'ом: chromedriver всегда держит CDP `Runtime.enable`, из-за чего аргументы
  console сериализуются, getter срабатывает → «Debugging Detected»; плюс
  `debuggerChecker` (timing `new Function('debugger')()`);
- проверяет `isTrusted` у событий (программный `el.click()` не проходит) и снимает
  отпечаток FingerprintJS.

Следствия для проекта: `register_user()` и вход `FlexyAiAPI.login()` падают на
первом же GET с «468 Client Error» — сломаны оба пути регистрации и login при
генерации (API генерации `api.flexyai.ru` WAF'ом не закрыт, пул с готовыми
`api_key` не задет). Параллельно сервер **снова включил подтверждение email** при
входе («Перед входом подтвердите свои данные на почте») — предпосылка ADR-003
«верификация отключена» перестала выполняться.

Эксперименты (07.11.2026) показали рабочий обход:

1. uc-браузер + инъекция **до загрузки страницы** (`Page.addScriptToEvaluateOnNewDocument`):
   маскировка всех console-методов (объекты не доходят до CDP-сериализации) +
   патч Function-конструктора против `debugger`-timing — челлендж проходит сам,
   без клика, за ~5 сек;
2. пройденные куки (`sl_jwt_sign`, `sl_jwt_session`, `sl-session`, `PHPSESSID`,
   `sl-challenge-server`) переносятся в обычную `requests.Session` — сервер
   принимает GET-страницы, `check_field`, `arm_reinit_session_multiple_form`,
   сабмит формы регистрации и формы входа (проверено end-to-end: аккаунт создан,
   вход ответил валидным JSON ARMember). К кукам не привязан User-Agent
   (регистрация прошла с UA Chrome/120 при куках от Chrome/157).

## Решение

Модуль **WAF-сессии** `src/waf_session.py` — единственный владелец знания про 468:

- `obtain_waf_cookies()` — поднимает uc-браузер (переиспользует
  `farm.setup_driver`), инъецирует контр-скрипт, ждёт появления формы ARMember
  (~5 сек, таймаут `WAF_CHALLENGE_TIMEOUT_SECONDS`), возвращает куки + UA.
  При непрохождении — тексты челленджа в лог (диагностика «гонки вооружений»);
- кэш кук на процесс (`threading.Lock`): переиспользуется всеми потоками
  (бот логинится из потоков `asyncio.to_thread`);
- `waf_request(session, method, url, ...)` — обёртка над HTTP-вызовом: при 468
  обновляет куки из кэша (или получает новые — еще один запуск браузера) и
  ретраит запрос один раз; повторный 468 → `WafBlockedError`
  (`src/errors/waf_errors.py`, наследник RuntimeError — существующая обработка
  в `generation.py` продолжает работать);
- защита от шторма запусков браузера (`WAF_MIN_OBTAIN_INTERVAL_SECONDS`).

Интеграция: `register_user()` и `FlexyAiAPI` (GET `/login`, verification-link,
`_post_ajax`) ходят через `waf_request` — WAF становится прозрачным для всей
фермы и бота, отдельные сессии протаскивать не нужно.

Корректировка путей регистрации (`src/farm.py`):

- **temp-mail (ADR-002) снова основной**: сервер требует подтверждение email,
  без письма аккаунт не входит. WAF-куки получает провайдер (свой запуск uc на
  челлендж), браузер temp-mail продолжает работать как раньше;
- **no-email (ADR-003) — fallback**: путь остаётся, но при включённой
  верификации прерывается сразу с понятной ошибкой («используйте temp-mail
  путь»), не сжигая попытки; «pure requests без браузера» больше нет —
  провайдер запускает браузер для первого получения кук.

Попутный фикс: `register_new_account()` проверяет результат `register_user()` —
при неудачной регистрации не ждёт письмо (раньше флоу зависал на
«Ждем появления письма» для несуществующего аккаунта).

## Рассмотренные альтернативы

1. **Полностью браузерная регистрация/вход (selenium-формы)** — отклонено:
   переделка `registration.py` и `api.py` целиком, медленнее; куки+requests
   работают и требуют минимальных изменений.
2. **curl_cffi / TLS-имперсонация Chrome без браузера** — отклонено: челлендж
   SafeLine — JS-челлендж (не TLS-фингерпринт), 468 стабилен для любого
   не-браузерного клиента; проверено на Googlebot/iPhone/curl UA.
3. **Реверс-инжиниринг challenge.js (PoW-протокол на pure Python)** — отклонено:
   113 КБ обфусцированного кода, меняется без предупреждения; uc-обход
   проходит стабильно.
4. **Прокидывать готовую сессию из фермы в каждый вызов** — отклонено:
   бот (`generation.py`) логинится в своих потоках без фермы; провайдер с
   кэшем покрывает оба сценария без изменения сигнатур вызывающего кода.

## Последствия

**Плюсы:**
- регистрация и вход снова работают; механизм один для фермы, CLI и бота;
- при следующем изменении челленджа падение локализовано в `waf_session.py`
  (тексты челленджа пишутся в лог).

**Минусы / цена:**
- первый запрос после старта процесса (и каждое протухание кук) запускает
  Chrome (~10–20 сек); в боте это происходит в потоке `asyncio.to_thread`;
  на машине должен быть рабочий Chrome — как и для фермы temp-mail;
- TTL кук неизвестен (JWT `sl_jwt_*`): кэш живёт до первого 468, обновление
  ленивое; при коротком TTL ферма будет гонять браузер чаще;
- контр-инъекция — «гонка вооружений» с SafeLine: обновление их challenge.js
  может снова сломать прохождение (диагностика — в лог, правка локальна);
- no-email путь перестал быть «без браузера» (уступка ADR-003, зафиксировано
  здесь).
